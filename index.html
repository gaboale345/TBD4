Fundamentación de la Práctica

Introducción y Objetivos del Proyecto

Por qué la manipulación sin control transaccional compromete la integridad del negocio.

Visión Global

Resumen e Introducción

En cualquier aplicación transaccional de ventas, cada operación modifica múltiples entidades vinculadas: registrar la cabecera de la venta, detallar los ítems comercializados y descontar las existencias del inventario.

Si alguno de estos pasos falla a medio camino, no es admisible conservar estados parciales (por ejemplo, haber descontado existencias sin emitir la venta, o vender sin descontar stock). La combinación sinérgica entre sentencias DML y el control TCL garantiza la atomicidad absoluta de las operaciones.

Objetivos Establecidos

Objetivo General: Gestionar transacciones y manipular registros de ventas mediante subconsultas y sentencias DML seguras en PostgreSQL instalado en Windows.

Objetivos Específicos:
  • Desplegar y aislar una base de datos de práctica (actividad4_ventas).
  • Aplicar sentencias INSERT, UPDATE y DELETE con cláusulas condicionales rigurosas.
  • Emplear subconsultas avanzadas (NOT IN, EXISTS, correlacionadas).
  • Dominar el control transaccional con BEGIN, COMMIT, ROLLBACK y SAVEPOINT.
  • Comprobar sistemáticamente los estados antes y después de cada cambio.
Marco Teórico y Taxonomía SQL

Conceptos Clave: DML vs TCL

DML transforma el estado de los datos; TCL decide si dicha transformación se hace irreversible o se descarta.

Arquitectura ACID

INSERT

Agrega nuevas tuplas a una tabla. Puede generar identificadores automáticamente con IDENTITY y devolver valores con RETURNING.

UPDATE

Modifica valores en registros preexistentes. Exige siempre una cláusula WHERE para evitar alteraciones accidentales masivas.

DELETE

Elimina registros bajo criterios específicos. Debe pre-validarse con SELECT previo para verificar cuántas filas serán afectadas.

SELECT / Subconsulta

Inspecciona y proyecta datos sin mutarlos. Una subconsulta anidada permite filtrar o calcular parámetros de forma dinámica.

BEGIN / COMMIT

BEGIN inicia el bloque de transacción aislada. COMMIT hace que todos los cambios sean definitivos y persistentes en disco.

ROLLBACK

Anula y deshace todas las operaciones realizadas desde el BEGIN, restaurando la base de datos a su estado prístino previo.

SAVEPOINT

Crea un punto de control intermedio. Permite ejecutar ROLLBACK TO SAVEPOINT para corregir un fallo parcial sin abortar el resto.

Modelo Relacional DDL

Creación de las Tablas Relacionales

Definición de claves primarias identity, restricciones CHECK y claves foráneas en cascada.

Estructura de Datos
01_creacion_tablas.sql
-- 1. Tabla de Clientes
CREATE TABLE clientes (
  id_cliente INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  nombre VARCHAR(100) NOT NULL,
  ciudad VARCHAR(60) NOT NULL
);

-- 2. Tabla de Productos con restricciones CHECK
CREATE TABLE productos (
  id_producto INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  nombre VARCHAR(100) NOT NULL,
  precio NUMERIC(10,2) NOT NULL CHECK (precio > 0),
  stock INTEGER NOT NULL CHECK (stock >= 0)
);

-- 3. Cabecera de Ventas
CREATE TABLE ventas (
  id_venta INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  id_cliente INTEGER NOT NULL REFERENCES clientes(id_cliente),
  fecha DATE NOT NULL DEFAULT CURRENT_DATE,
  estado VARCHAR(20) NOT NULL DEFAULT 'REGISTRADA'
);

-- 4. Detalle de Ventas
CREATE TABLE detalle_venta (
  id_detalle INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  id_venta INTEGER NOT NULL REFERENCES ventas(id_venta),
  id_producto INTEGER NOT NULL REFERENCES productos(id_producto),
  cantidad INTEGER NOT NULL CHECK (cantidad > 0),
  precio_unitario NUMERIC(10,2) NOT NULL CHECK (precio_unitario > 0)
);

Ejercicio 1 • Control Transaccional

Registrar Venta Atómica con COMMIT

Uso de CTE y RETURNING para encadenar inserción de venta, detalle y rebaja de inventario.

CTE + RETURNING
ejercicio1_commit.sql
BEGIN;

-- 1. Insertamos cabecera de venta capturando id_venta generado
WITH nueva_venta AS (
  INSERT INTO ventas (id_cliente)
  SELECT id_cliente FROM clientes WHERE nombre = 'Ana Pérez'
  RETURNING id_venta
)
-- 2. Insertamos el detalle asociando la venta y el producto
INSERT INTO detalle_venta (id_venta, id_producto, cantidad, precio_unitario)
SELECT nv.id_venta, p.id_producto, 2, p.precio
FROM nueva_venta nv CROSS JOIN productos p
WHERE p.nombre = 'Teclado';

-- 3. Actualizamos inventario de teclados (descuento de 2 unidades)
UPDATE productos SET stock = stock - 2
WHERE nombre = 'Teclado' AND stock >= 2;

COMMIT;

SELECT nombre, stock FROM productos WHERE nombre = 'Teclado';

Ejercicio 2 • Subconsultas DML

Aumento de Precios con Subconsulta NOT IN

Incrementar un 10% el precio de aquellos productos que todavía no registran ventas.

Filtrado Dinámico
ejercicio2_subconsulta.sql
BEGIN;

-- Verificación del catálogo antes del cambio
SELECT nombre, precio FROM productos ORDER BY id_producto;

-- Actualizamos con aumento del 10% solo a los no vendidos
UPDATE productos
SET precio = ROUND(precio * 1.10, 2)
WHERE id_producto NOT IN (
  SELECT id_producto FROM detalle_venta
);

-- Inspección del resultado esperado
SELECT nombre, precio FROM productos ORDER BY id_producto;

COMMIT;

Ejercicio 3 • Tolerancia a Fallos

Simulación de Error y Reversión con ROLLBACK

Comprobación de que las modificaciones dentro de un bloque transaccional no persisten si se abortan.

Reversión Total
ejercicio3_rollback.sql
BEGIN;

-- 1. Error humano: Se intenta modificar el precio del monitor a Bs 1.00
UPDATE productos SET precio = 1.00 WHERE nombre = 'Monitor';

-- 2. Durante la transacción se observa el valor erróneo de Bs 1.00
SELECT nombre, precio FROM productos WHERE nombre = 'Monitor';

-- 3. Detectamos la anomalía y cancelamos la operación
ROLLBACK;

-- 4. Verificación: El monitor vuelve a su valor original de Bs 1045.00
SELECT nombre, precio FROM productos WHERE nombre = 'Monitor';

Ejercicio 4 • Puntos de Control

Reversión Parcial mediante SAVEPOINT

Deshacer únicamente una sub-operación defectuosa sin perder los cambios correctos previos.

Punto de Control
ejercicio4_savepoint.sql
BEGIN;

-- 1. Modificación correcta: Incrementamos stock del Mouse (+5)
UPDATE productos SET stock = stock + 5 WHERE nombre = 'Mouse';

-- 2. Establecemos un punto de restauración seguro
SAVEPOINT antes_del_segundo_cambio;

-- 3. Modificación no deseada: Ponemos en 0 el stock del USB
UPDATE productos SET stock = 0 WHERE nombre = 'Memoria USB';

-- 4. Revertimos SOLO el cambio erróneo volviendo al savepoint
ROLLBACK TO SAVEPOINT antes_del_segundo_cambio;

-- 5. Confirmamos la transacción (conservando el +5 del Mouse)
COMMIT;

SELECT nombre, stock FROM productos
WHERE nombre IN ('Mouse', 'Memoria USB') ORDER BY nombre;

Ejercicio 6 • DML Seguro

Eliminación Controlada con Cláusula NOT EXISTS

Protocolo de seguridad: Inspección selectiva previa antes de ejecutar DELETE para preservar la integridad referencial.

DELETE Protegido
ejercicio6_delete_controlado.sql
BEGIN;

-- Paso 1: Comprobación previa. Verificamos quién cumple la condición
SELECT c.id_cliente, c.nombre FROM clientes c
WHERE NOT EXISTS (
  SELECT 1 FROM ventas v WHERE v.id_cliente = c.id_cliente
) AND c.nombre = 'Luis Rojas';

-- Paso 2: Eliminación con exactamente la misma condición verificada
DELETE FROM clientes c
WHERE c.nombre = 'Luis Rojas'
AND NOT EXISTS (
  SELECT 1 FROM ventas v WHERE v.id_cliente = c.id_cliente
);

-- Paso 3: Verificación de permanencia de Ana y María
SELECT * FROM clientes ORDER BY id_cliente;

COMMIT;

Ejercicio 7 • Patrón Industrial Avanzado

Transacción Segura y Atómica para Descontar Stock

Validar existencias y descontar con UPDATE ... RETURNING antes de autorizar la emisión de la venta.

Stock Atómico
ejercicio7_transaccion_segura.sql
BEGIN;

-- 1. Primero intentamos descontar el stock con condición estricta
WITH descontado AS (
  UPDATE productos
  SET stock = stock - 3
  WHERE nombre = 'Mouse' AND stock >= 3
  RETURNING id_producto, precio
),
-- 2. Solamente si el descuento generó una fila, creamos la venta
nueva_venta AS (
  INSERT INTO ventas (id_cliente)
  SELECT c.id_cliente FROM clientes c
  WHERE c.nombre = 'María Flores'
    AND EXISTS (SELECT 1 FROM descontado)
  RETURNING id_venta
)
-- 3. Detallamos la venta utilizando los valores devueltos
INSERT INTO detalle_venta (id_venta, id_producto, cantidad, precio_unitario)
SELECT v.id_venta, d.id_producto, 3, d.precio
FROM nueva_venta v CROSS JOIN descontado d;

SELECT nombre, stock FROM productos WHERE nombre = 'Mouse';

COMMIT;

Auditoría y Cierre

Comprobación General de Ventas e Inventario

Consulta consolidada con JOIN, LEFT JOIN, SUM y COALESCE para certificar la consistencia del sistema.

Auditoría Exitosa
13_comprobacion_final.sql
-- 1. Resumen consolidado de todas las ventas emitidas
SELECT 
  v.id_venta, 
  c.nombre AS cliente, 
  v.fecha,
  COALESCE(SUM(d.cantidad * d.precio_unitario), 0) AS total_bs
FROM ventas v
JOIN clientes c ON c.id_cliente = v.id_cliente
LEFT JOIN detalle_venta d ON d.id_venta = v.id_venta
GROUP BY v.id_venta, c.nombre, v.fecha
ORDER BY v.id_venta;

-- 2. Estado definitivo del inventario de productos
SELECT nombre, precio, stock FROM productos ORDER BY id_producto;

Síntesis y Buenas Prácticas

Recomendaciones Profesionales y Conclusiones

Lecciones aprendidas sobre gestión transaccional segura en entornos de producción.

Buenas Prácticas

Recomendaciones para Evitar Errores

  • Pre-validación con SELECT: Antes de lanzar un UPDATE o DELETE, ejecutar un SELECT con exactamente la misma condición WHERE para auditar las filas afectadas.
  • Encapsulamiento Explícito: Trabajar siempre dentro de bloques BEGIN ... COMMIT al manipular datos de negocio críticos.
  • Manejo de Transacciones Abortadas: En PostgreSQL, cualquier fallo de sintaxis o restricción deja la transacción en estado abortado (aborted transaction), requiriendo un ROLLBACK forzoso antes de reanudar.
  • Verificación de Retorno: Garantizar que las deducciones de stock se hayan efectuado realmente con RETURNING antes de persistir la cabecera de venta.

Conclusiones de la Práctica

La manipulación de bases de datos relacionales no consiste meramente en insertar o borrar registros, sino en garantizar que la operación global tenga sentido de negocio y preserve el estado consistente del sistema.

Con COMMIT confirmamos cambios atómicos; con ROLLBACK prevenimos catástrofes ante errores imprevistos; y con SAVEPOINT ganamos flexibilidad granular para aislar fallas sin perder el progreso anterior. Las subconsultas demuestran ser un instrumento idóneo para modular cambios dinámicos y seguros.
